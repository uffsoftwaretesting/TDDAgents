# Especificação Técnica: API de Validação de CPF

## 1. Visão Geral do Sistema  
A API REST “/validate-cpf” recebe um JSON com um campo `cpf` (string, com ou sem máscara) e retorna um JSON indicando se o CPF é válido, aplicando Clean Architecture (domain, application, infrastructure, interfaces), injeção de dependência, validação de entrada com Pydantic e testes TDD em pytest.

## 2. Estruturas de Dados e Interfaces

### 2.1 Domain Layer  
- **Value Object `Cpf`**  
  - Campo: `value: str` (apenas dígitos após normalização)  
  - Responsabilidade:  
    - Normalizar (remover pontos e traços)  
    - Validar comprimento exato (11 dígitos)  
    - Validar dígitos verificadores conforme algoritmo oficial  
  - Exceções específicas:  
    - `InvalidCpfFormat` (formato incorreto, caracteres não numéricos, comprimento)  
    - `InvalidCpfCheckDigits` (falha na validação de dígitos verificadores)  

- **Interface de porta `ICpfValidator`**  
  - Método: `validate(cpf: str) -> bool`  
  - Sem dependências externas  

### 2.2 Application Layer  
- **Use Case `ValidateCpfUseCase`**  
  - Método público: `execute(cpf: str) -> bool`  
  - Recebe um `cpf: str` cru  
  - Delegação para `ICpfValidator.validate(cpf)`  
  - Retorna `True` ou `False` sem lançar exceções  

### 2.3 Infrastructure Layer  
- **Adapter `CpfValidatorAdapter`**  
  - Implementa `ICpfValidator`  
  - Utiliza biblioteca externa (`validate-docbr` ou `python-cpf`)  
  - Normaliza entrada antes de chamar a biblioteca  
  - Converte erros da biblioteca em retorno booleano ou exceções do Domain, conforme mapeamento  

- **Configuração `Settings`**  
  - Classe baseada em Pydantic `BaseSettings`  
  - Carrega variáveis de `.env` (ex.: configurações de ambiente, opções de log)  

### 2.4 Interfaces / Presentation Layer  
- **Modelos Pydantic**  
  - `CpfInput`:  
    - Campo `cpf: str`  
    - Validação automática de tipo e não-vazio  
  - `CpfOutput`:  
    - Campo `valid: bool`  

- **Router `/validate-cpf`**  
  - Método: `POST`  
  - Recebe `CpfInput` no corpo  
  - Injeta `ValidateCpfUseCase` via dependência  
  - Chama `use_case.execute(cpf)`  
  - Responde com 200 e `CpfOutput(valid=...)`  
  - Pydantic gera 422 para payloads inválidos  

## 3. Casos de Borda e Validações (Edge Cases)

- Payload ausente, malformado ou com campo `cpf`  
  - Pydantic: HTTP 422  
- `cpf` nulo ou tipo não-string  
  - HTTP 422 pelo Pydantic  
- `cpf` string vazia  
  - Pydantic aceita, mas `Cpf` lança `InvalidCpfFormat` → mapeado como `valid: false` com HTTP 200  
- Máscara incorreta ou caracteres não numéricos  
  - `Cpf` lança `InvalidCpfFormat` → `false`  
- Comprimento diferente de 11 dígitos após normalização  
  - `InvalidCpfFormat` → `false`  
- Dígitos verificadores inválidos  
  - `InvalidCpfCheckDigits` → `false`  
- Todos os dígitos iguais (ex.: “11111111111”)  
  - Considerado inválido pelo algoritmo → `false`  
- Biblioteca externa indisponível ou falha interna  
  - Adapter captura exceção e converte para `false` (não propaga erro)  
- Performance: entradas muito longas  
  - Truncar após remoção de máscara para verificação de formato, lançar `InvalidCpfFormat`  

## 4. Contexto Técnico  
- Linguagem: Python 3.x  
- Framework HTTP: FastAPI + Uvicorn  
- Validação de dados: Pydantic  
- Arquitetura: Clean Architecture (domain, application, infrastructure, interfaces)  
- Paradigma: TDD com pytest  
- Injeção de dependência: FastAPI Depends ou similar  
- Configuração: `.env` via Pydantic BaseSettings  
- Documentação automática: OpenAPI/Swagger fornecida pelo FastAPI  
- Logging: módulo `logging` padrão do Python  
- Código limpo: tipagem estática, nomes autoexplicativos, métodos pequenos
