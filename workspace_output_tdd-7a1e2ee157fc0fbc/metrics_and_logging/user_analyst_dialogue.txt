[Analista]: 📝 Checklist de Requisitos Técnico para API de Conversão Markdown → HTML

1. Projeto & Setup
• Inicializar repositório Git e ambiente virtual (venv).
• Configurar entrypoint (e.g., main.py) com instância FastAPI.
• Estruturar diretórios:
– app/
• config/
• schemas/
• services/
• routes/
– tests/

2. Variáveis de Ambiente & Configuração
• Utilizar pydantic BaseSettings ou python-dotenv para carregar .env.
• .env.example contendo (ao mínimo):
– APP_NAME (string)
– ENV (development|production)
– DEBUG (bool)
– HOST (string)
– PORT (int)
• Validar carregamento de variáveis obrigatórias e tipos.

3. Dependências (requirements.txt)
• fastapi
• uvicorn
• pydantic
• python-dotenv
• markdown2 (ou markdown)
• pytest
• httpx
• (opcional) black, isort

4. Schemas & Validação
• Request Schema (MarkdownRequest):
– markdown_content: str (não vazio, tamanho máximo configurável).
• Response Schema (HTMLResponse):
– html_content: str
• Error Schema (ErrorResponse):
– code: int
– message: str

5. Service de Conversão
• Função convert_markdown_to_html(markdown_content: str) -> str:
– Usa biblioteca markdown2.markdown() ou equivalente.
– Trata possíveis exceções internas.

6. Rotas / Endpoints
• POST /convert
– Body: MarkdownRequest
– Response: HTMLResponse
– Status 200: conversão bem-sucedida
– Status 4xx: erro de validação de input
– Status 5xx: erro interno de conversão

7. Tratamento de Erros & Respostas Padronizadas
• Middleware ou handler para RequestValidationError → retornos 422 com ErrorResponse.
• Exception Handler genérico para Exception → 500 com ErrorResponse.
• Formato de resposta:
{
"success": bool,
"data": {} | null,
"error": ErrorResponse | null
}

8. Testes (TDD)
• Unit tests para:
– Service de conversão com casos simples e vazios.
– Config loader: cenários com .env faltando ou tipos incorretos.
• Integration tests usando httpx TestClient para:
– POST /convert com payload válido → status 200 e HTML esperado.
– Payload inválido (campo ausente ou não-string) → 422.
– Simular erro interno (mock da biblioteca) → 500.

9. Documentação & Exemplos
• README.md com instruções de setup, execução e testes.
• .env.example para configuração.
• Exemplo de chamada usando curl ou HTTPie.

10. Boas Práticas & Qualidade de Código
• Linter (flake8/black) e type hints (mypy opcional).
• Logging configurado via variáveis de ambiente.
• Separação clara de responsabilidades (routes apenas roteia; services contêm lógica).

[Analista]: 📝 Checklist de Requisitos Técnicos (Clean Architecture) para API de
            Conversão Markdown → HTML

1. Arquitetura Clean
• Camadas:
– Domain: entidades e regras de negócio (ex: MarkdownContent, HTMLContent).
– Application (Use Cases): casos de uso (ex: ConvertMarkdownUseCase).
– Interface Adapters: conversão de dados entre camadas (ex: controllers, schemas,
mappers).
– Frameworks & Drivers: FastAPI, bancos de dados, bibliotecas externas.
• Cada camada isolada em diretórios distintos sob src/:
src/
├── domain/
├── application/
├── adapters/
│     ├── http/
│     └── persistence/ (se houver)
└── infrastructure/

2. Projeto & Setup
• Git com branch main/prod e develop.
• Ambiente virtual (venv/venv).
• Entry point: src/infrastructure/main.py (instância FastAPI).
• Configurar configuração de logging na infraestrutura.

3. Variáveis de Ambiente & Configuração
• Utilizar pydantic’s BaseSettings para carregar .env.
• arquivo .env (não versionado) + .env.example (versionado) com exemplos:
– APP_NAME
– ENV (development|production)
– DEBUG
– HOST
– PORT
• Validar tipos e presença de variáveis obrigatórias.
