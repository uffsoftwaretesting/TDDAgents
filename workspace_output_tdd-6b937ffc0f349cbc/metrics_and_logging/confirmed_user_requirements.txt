REQUISITOS ENVIADOS PELO USUÁRIO
================================================================================
[Usuário]: Como desenvolvedor backend experiente, projete e implemente uma API REST
           utilizando FastAPI em Python, seguindo rigorosamente os princípios de Clean
           Architecture com separação clara de camadas tanto no diretório src quanto em
           tests, garantindo baixo acoplamento, alta coesão e uso de injeção de
           dependência, sem colocar lógica de negócio nas rotas, organizando o projeto
           em domain (regras de negócio e entidades puras), application (casos de uso),
           infrastructure (integrações externas como validate-docbr ou python-cpf) e
           interfaces ou presentation (controladores FastAPI), com a estrutura de testes
           espelhando a de src; o objetivo é expor um endpoint POST /validate-cpf que
           receba um JSON com o campo cpf como string e retorne se o CPF é válido ou não
           utilizando uma biblioteca confiável, aceitando CPFs com e sem máscara como
           123.456.789-09 e 12345678909, validando corretamente dígitos verificadores,
           rejeitando CPFs com entradas inválidas, como strings vazias, campos ausentes
           ou nulos, caracteres não numéricos inesperados e etc; o contrato da API deve
           retornar 200 para requisições válidas com um JSON como { "valid": true } e
           422 para payloads inválidos usando validação automática com Pydantic; o
           desenvolvimento deve seguir TDD com implementação exclusiva de testes
           unitários usando pytest cobrindo todos os cenários relevantes e com estrutura
           espelhada de diretórios; além disso, a aplicação deve incluir configuração
           completa de Docker para desenvolvimento (com hot reload e volume mount) e
           produção (com imagem otimizada e build multi-stage), com Dockerfile e
           opcionalmente docker-compose, e um pipeline de CI com GitHub Actions
           incluindo instalação de dependências, execução de testes, lint com flake8 e
           opcionalmente build da imagem, seguindo boas práticas como tipagem estática,
           uso de .env, código limpo e suporte à documentação automática via
           OpenAPI/Swagger.
[Analista]: Checklist de Requisitos Técnico (Clean Architecture + TDD + Docker + CI):

1. Estrutura de Diretórios:
1.1. src/
• domain/
• application/
• infrastructure/
• interfaces/ (ou presentation/)
• main.py (entrypoint FastAPI)
• core/ (configuração, .env loader)
1.2. tests/ (espelhando src):
• domain/
• application/
• infrastructure/
• interfaces/

2. Domain Layer:
2.1. Entidade CPF:
• Classe CPF(value: str)
• Validação de formato (apenas dígitos após sanitização)
• Cálculo dos dígitos verificadores
• Exceções customizadas para invalid CPF
2.2. Regras puras, sem dependências externas

3. Application Layer:
3.1. Caso de Uso ValidateCpfUseCase:
• Interface IValidateCpfUseCase
• Implementação que recebe um repositório/porta de validação
• Método execute(cpf: str) -> bool
3.2. Definição de portas/interfaces (para injeção de dependência)

4. Infrastructure Layer:
4.1. Adapter para biblioteca externa (e.g. validate-docbr ou python-cpf)
• Implementa interface IValidateCpfRepository
• Método validate(cpf: str) -> bool
4.2. Isolamento de dependência externa

5. Interfaces/Presentation Layer:
5.1. FastAPI Router (/validate-cpf):
• Pydantic model ValidateCpfRequest { cpf: str }
• Pydantic model ValidateCpfResponse { valid: bool }
• Endpoint POST /validate-cpf
– Recebe JSON
– Chama ValidateCpfUseCase
– Retorna 200 + { "valid": <bool> }
– Resposta 422 para payload inválido (Pydantic)
5.2. Nenhuma regra de negócio nas rotas
5.3. OpenAPI gerada automaticamente (/docs)

6. Injeção de Dependência:
• Configurar container simples (FastAPI Depends)
• Registrar implementação de IValidateCpfRepository e IValidateCpfUseCase

7. Validações e Tratamento de Erros:
• CPF nulo, ausente ou vazio → Pydantic 422
• Caracteres não numéricos inesperados → sanitização ou 422
• Exceções internas → tratamento para 500 genérico

8. TDD e Tests Unitários (pytest):
8.1. tests/domain/test_cpf_entity.py
• Cenários: formato válido, inválido, trivial, borda
8.2. tests/application/test_validate_cpf_usecase.py
• Mock do repositório
8.3. tests/infrastructure/test_validate_docbr_adapter.py
• Mock da biblioteca externa
8.4. tests/interfaces/test_api.py
• TestClient para POST /validate-cpf
• Casos: válido, inválido, payload mal-formado
8.5. Cobertura completa de fluxos happy path e erros

9. Docker:
9.1. Dockerfile (dev):
• Base python:3.x
• Instalar dependências
• CMD uvicorn main:app --reload --host 0.0.0.0
• Volume mount para src e tests
9.2. Dockerfile (prod multi-stage):
• Builder: instala deps, roda lint/tests
• Runtime: copia apenas binários e src
• Executa uvicorn sem reload
9.3. docker-compose.yml (dev):
• Serviço app com hot-reload
• Variáveis de ambiente via .env

10. CI/CD (GitHub Actions):
10.1. Workflow:
• Trigger on push e pull_request
• Steps:
– checkout
– setup-python
– install dependencies
– flake8 lint
– pytest --cov
– (opcional) docker build --target prod
10.2. Artefatos de cobertura e relatórios

11. Boas Práticas:
• Tipagem estática (mypy opcional)
• Arquivo .env para configuração
• README com instruções de setup, testes e deploy
• Clean code: nomes claros, SOLID, DRY
