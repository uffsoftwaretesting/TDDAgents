REQUISITOS ENVIADOS PELO USUÁRIO
================================================================================
[Usuário]: Como desenvolvedor backend experiente, projete e implemente uma API REST
           utilizando FastAPI em Python, seguindo rigorosamente os princípios de Clean
           Architecture com separação clara de camadas tanto no diretório src quanto em
           tests, garantindo baixo acoplamento, alta coesão e uso de injeção de
           dependência, sem colocar lógica de negócio nas rotas, organizando o projeto
           em domain (regras de negócio e entidades puras), application (casos de uso),
           infrastructure (integrações externas como validate-docbr ou python-cpf) e
           interfaces ou presentation (controladores FastAPI), com a estrutura de testes
           espelhando a de src; o objetivo é expor um endpoint POST /validate-cpf que
           receba um JSON com o campo cpf como string e retorne se o CPF é válido ou não
           utilizando uma biblioteca confiável, aceitando CPFs com e sem máscara como
           123.456.789-09 e 12345678909, validando corretamente dígitos verificadores,
           rejeitando CPFs com todos os dígitos iguais, e tratando entradas inválidas
           como strings vazias, campos ausentes ou nulos e caracteres não numéricos
           inesperados; o contrato da API deve retornar 200 para requisições válidas com
           um JSON como { "valid": true } e 422 para payloads inválidos usando validação
           automática com Pydantic; o desenvolvimento deve seguir TDD com implementação
           exclusiva de testes unitários usando pytest cobrindo todos os cenários
           relevantes e com estrutura espelhada de diretórios; além disso, a aplicação
           deve incluir configuração completa de Docker para desenvolvimento (com hot
           reload e volume mount) e produção (com imagem otimizada e build multi-stage),
           com Dockerfile e opcionalmente docker-compose, e um pipeline de CI com GitHub
           Actions incluindo instalação de dependências, execução de testes, lint com
           flake8 ou ruff e opcionalmente build da imagem, seguindo boas práticas como
           tipagem estática, uso de .env, código limpo e suporte à documentação
           automática via OpenAPI/Swagger.
[Analista]: Checklist de Requisitos Técnico – API de Validação de CPF com FastAPI e
            Clean Architecture

1. Estrutura do Projeto (src/)
• src/domain/
– Definição de entidade CPF pura (sem dependências externas).
– Validação de regras de negócio (dígitos verificadores, rejeição de sequências
idênticas).
• src/application/
– Casos de uso: ValidateCpfUseCase com interface (porta) e implementação.
• src/infrastructure/
– Adapter para biblioteca de validação (ex: python-cpf ou validate-docbr).
– Configuração de injeção de dependência.
• src/interfaces/ (ou presentation/)
– Controlador FastAPI (router) apenas orquestrando caso de uso.
– Não conter lógica de negócio.
• src/config/
– Leitura de variáveis de ambiente (.env).
– Configuração de instância da aplicação FastAPI.

2. Modelos e Validação de Payload (Pydantic)
• Model Pydantic para Request (campo cpf: str).
• Model Pydantic para Response ({ "valid": bool }).
• Configurar validação automática de payloads inválidos (422).
• Testar casos: campo ausente, nulo, string vazia, caracteres não numéricos.

3. Endpoint POST /validate-cpf
• Rota: POST /validate-cpf
• Input: JSON { "cpf": "<string>" }
• Output (200): { "valid": true/false }
• Errors 422: payload inválido via validação Pydantic.
• Separar lógica de parsing (remover máscara) e validação de regras de negócio.

4. Regras de Negócio de Validação CPF
• Aceitar CPFs com e sem máscara (ex: 123.456.789-09 e 12345678909).
• Rejeitar sequências com todos dígitos iguais.
• Validar corretamente dígitos verificadores.

5. Injeção de Dependência
• Definir interfaces para validação de CPF.
• Registrar implementações concretas no container (ex: FastAPI Depends).
• Permitir swap de implementação em testes (mock).

6. Test-Driven Development (pytest)
Estrutura de testes espelhada em tests/:
• tests/domain/test_cpf_entity.py – regras de negócio.
• tests/application/test_validate_cpf_usecase.py – casos de uso.
• tests/infrastructure/test_cpf_adapter.py – integração com biblioteca.
• tests/interfaces/test_controller.py – testes de rota (TestClient).

Cenários obrigatórios:
• CPF válido sem máscara.
• CPF válido com máscara.
• CPF inválido dígito verificador.
• CPF de sequência idêntica.
• Payload ausente, nulo, vazio, caracteres inválidos.

7. Docker
Dev:
• Dockerfile com hot reload (uvicorn --reload).
• Volume mount src e tests.
• docker-compose.yml opcional para app e .env.

Prod:
• Multi-stage build (base python-slim, copiar apenas src e instalar deps).
• Rodar uvicorn sem reload.
• Construção de imagem otimizada.

8. Integração Contínua (GitHub Actions)
• Workflow que aciona em push e PR.
• Passos: checkout, setup Python, install deps, lint (flake8 ou ruff), pytest.
• Opcional: build da imagem Docker.

9. Boas Práticas
• Tipagem estática (type hints em todos módulos).
• Código limpo e organizado (linters e formatters).
• Uso de .env para configuração.
• Documentação automática via OpenAPI/Swagger (FastAPI gera automaticamente).
