# Especificação Técnica: API de Validação de CPF

## 1. Visão Geral do Sistema
Uma API REST em Python utilizando FastAPI que expõe o endpoint POST /validate-cpf. A validação de CPF segue Clean Architecture com camadas claras de domain, application, infrastructure e interfaces. A lógica de negócio (validação de dígitos verificadores e rejeição de sequências idênticas) fica no domínio, sem acoplamento às rotas. O payload é validado por Pydantic e o resultado é `{ "valid": true|false }`. Entradas inválidas geram HTTP 422.

## 2. Estruturas de Dados e Interfaces

### 2.1 Camada Domain
- Entidade CPF (classe imutável)
  - Propriedades:
    - raw: str
    - digits: str (somente números, length == 11)
  - Regras de negócio:
    - Rejeitar CPFs com todas as sequências iguais (`00000000000`, etc.)
    - Validar dígitos verificadores conforme algoritmo oficial
- Interface `CPFValidator` (porta)
  - Método: `is_valid(cpf: str) -> bool`

### 2.2 Camada Application
- Interface `ValidateCpfUseCase` (porta)
  - Método: `execute(cpf: str) -> bool`
- Implementação `ValidateCpfInteractor` (caso de uso)
  - Depende de `CPFValidator`
  - Recebe string de CPF, delega limpeza e validação ao domínio/infrastructure e retorna boolean

### 2.3 Camada Infrastructure
- Adapter concreto `ValidateDocbrCpfValidator` ou `PythonCpfValidator`
  - Implementa `CPFValidator`
  - Internamente usa biblioteca externa (`validate-docbr` ou `python-cpf`)
- Configuração de Injeção de Dependência
  - Provedor FastAPI com `Depends` para `CPFValidator` e `ValidateCpfUseCase`

### 2.4 Camada Interfaces (Presentation)
- Ponto de entrada FastAPI
  - Router: `/validate-cpf`
  - Controller: recebe `ValidateCpfRequest`, injeta `ValidateCpfUseCase`, chama `execute()`, retorna `ValidateCpfResponse`
  - Não contém lógica de negócio

### 2.5 Models Pydantic
- ValidateCpfRequest
  - cpf: str
  - validações automáticas: campo obrigatório, não nulo
- ValidateCpfResponse
  - valid: bool

### 2.6 Configuração
- Leitura de .env via python-dotenv ou decouple
- Instância FastAPI configurada em `src/config/app.py`
- Registro de rotas e providers de DI

## 3. Casos de Borda e Validações (Edge Cases)
- Payload ausente ou campo `cpf` faltando → HTTP 422 (Pydantic)
- Campo `cpf` = null → HTTP 422
- Campo `cpf` = `""` (string vazia) → HTTP 422
- Campo com caracteres inválidos (letras, símbolos além de `.` e `-`) → HTTP 422
- CPF com máscara ou sem máscara:
  - `"123.456.789-09"` → limpo para `"12345678909"`
  - `"12345678909"` → uso direto
- CPF com sequência de dígitos iguais (`"11111111111"`) → retorna `{ "valid": false }` (200)
- CPF com dígito verificador incorreto → `{ "valid": false }` (200)
- CPF válido → `{ "valid": true }` (200)
- Erros internos não previstos → HTTP 500 ou handler global (log e retorno de erro genérico)
