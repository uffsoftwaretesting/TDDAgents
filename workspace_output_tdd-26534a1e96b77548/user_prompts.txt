1. Como desenvolvedor backend, quero construir uma API REST utilizando FastAPI que
   exponha um endpoint POST /validate-cpf que receba um JSON contendo o campo cpf do
   tipo string e retorne se o CPF informado é válido ou inválido, utilizando uma
   biblioteca Python especializada em validação de documentos brasileiros, como
   validate-docbr ou python-cpf, para realizar a verificação dos dígitos validadores e
   das regras formais do CPF, evitando a necessidade de reimplementar manualmente essa
   lógica e garantindo maior confiabilidade da validação. A aplicação deve seguir os
   princípios de Clean Architecture, organizando o código em camadas bem definidas como
   domain, application, infrastructure e interface, separando claramente regras de
   negócio, casos de uso e dependências externas, de forma que a lógica de validação
   possa ser reutilizada e testada independentemente do framework web. A API deve
   aceitar CPFs informados tanto com máscara quanto sem máscara, como 123.456.789-09 ou
   12345678909, e deve tratar corretamente diferentes cenários de entrada, incluindo
   CPFs válidos, CPFs inválidos por erro nos dígitos verificadores, CPFs compostos por
   todos os dígitos iguais como 111.111.111-11 que são considerados inválidos por
   definição, entradas contendo caracteres inesperados não numéricos, strings vazias,
   campos cpf ausentes no corpo da requisição ou valores nulos. O endpoint deve retornar
   respostas HTTP adequadas seguindo boas práticas de APIs REST, retornando status code
   200 quando a requisição estiver bem formada e incluindo no corpo da resposta um JSON
   indicando o CPF recebido e o resultado da validação, e retornando status code 422
   quando o payload da requisição estiver malformado ou violar as regras de validação do
   schema definidas com Pydantic, utilizando o mecanismo de validação automática do
   FastAPI. O projeto deve incluir um arquivo .env.example documentando todas as
   variáveis de ambiente utilizadas pela aplicação, permitindo fácil configuração em
   diferentes ambientes. A aplicação também deve ser totalmente containerizada,
   incluindo um Dockerfile otimizado para execução da API e um arquivo
   docker-compose.yml que permita subir o serviço localmente de forma simples para
   desenvolvimento e testes. O desenvolvimento deve seguir a metodologia TDD, com
   implementação inicial de testes unitários que cubram todos os cenários esperados de
   validação do CPF e validação de entrada da API, garantindo alta cobertura de testes e
   evitando a implementação de testes de integração ou testes end-to-end neste escopo
   inicial. Por fim, o repositório deve incluir uma pipeline de integração contínua
   utilizando GitHub Actions que execute automaticamente a instalação das dependências,
   rode os testes unitários, valide o build da aplicação e garanta que o projeto
   permaneça estável a cada novo commit ou pull request.

[Analista]: Checklist de Requisitos Técnico e Testável para API de Validação de CPF

1. Organização do Projeto
• Inicializar repositório Git
• Criar estrutura de pastas:
– domain/ (entidades e regras de negócio de CPF)
– application/ (casos de uso: ValidateCPFUseCase)
– infrastructure/ (integrações com biblioteca validate-docbr ou python-cpf)
– interface/ (FastAPI routers, Pydantic schemas)

2. Configuração de Ambiente
• Adicionar arquivo .env.example com variáveis:
– APP_PORT
– LOG_LEVEL
– OUTRAS_ENV
• Carregar variáveis via python-dotenv ou similar

3. Dependências e Ferramentas
• FastAPI e Uvicorn
• Biblioteca de validação de CPF (validate-docbr ou python-cpf)
• Pydantic para schemas e validação automática
• pytest e pytest-cov para testes unitários
• GitHub Actions para CI
• Docker e docker-compose

4. Domain Layer
• Definir entidade CPF
• Implementar regras de negócio independentes de biblioteca e framework
• Cobrir casos:
– CPF válido (com ou sem máscara)
– Dígitos verificadores incorretos
– Todos dígitos iguais
– Entrada vazia, nula ou caracteres não numéricos

5. Application Layer (Use Case)
• Classe ValidateCPFUseCase:
– Recebe string de CPF bruta
– Normaliza (remove máscara)
– Invoca serviço de validação da infrastructure
– Retorna objeto de resultado (cpf_original, cpf_formatado, is_valid)

6. Infrastructure Layer
• Serviço de Validação:
– Adapter para biblioteca escolhida
– Implementar interface comum com métodos: is_valid(cpf: str) -> bool

7. Interface Layer (API)
• Definir Pydantic schema para request:
– cpf: str (obrigatório)
• Definir Pydantic schema para response:
– cpf: str
– valid: bool
• Endpoint POST /validate-cpf:
– 200 OK: corpo com {"cpf": "…", "valid": true/false}
– 422 Unprocessable Entity: payload malformado ou campo ausente
• Tratar exceções e erros de validação automáticos do FastAPI

8. Testes Unitários (TDD)
• Domain: todos os cenários de validação de CPF
• Application: casos de uso chamando corretamente o serviço de validação
• Infrastructure: adapter mapeando resultados da biblioteca
• Interface: usando TestClient do FastAPI para:
– Enviar CPF válido mascarado e não mascarado
– Enviar CPF inválido (dígitos, todos iguais)
– Enviar payload sem campo cpf, vazio, caracteres inválidos
– Asserir status codes e corpos de resposta
• Cobertura mínima: 90%

9. Containerização
• Dockerfile otimizado (imagem python:3.x-slim)
• docker-compose.yml para subir serviço API com:
– build da imagem
– variáveis de ambiente do .env
– mapeamento de porta

10. Integração Contínua (GitHub Actions)
• Workflow que executa em push e pull_request:
– Checa out e configura Python
– Instala dependências
– Executa pytest com cobertura
– Lint (opcional)
– Build Docker (opcional)
