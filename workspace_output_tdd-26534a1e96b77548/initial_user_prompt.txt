PROMPT INICIAL ENVIADO PELO USUARIO
================================================================================
Como desenvolvedor backend, quero construir uma API REST utilizando FastAPI que
exponha um endpoint POST /validate-cpf que receba um JSON contendo o campo cpf
do tipo string e retorne se o CPF informado é válido ou inválido, utilizando uma
biblioteca Python especializada em validação de documentos brasileiros, como
validate-docbr ou python-cpf, para realizar a verificação dos dígitos
validadores e das regras formais do CPF, evitando a necessidade de reimplementar
manualmente essa lógica e garantindo maior confiabilidade da validação. A
aplicação deve seguir os princípios de Clean Architecture, organizando o código
em camadas bem definidas como domain, application, infrastructure e interface,
separando claramente regras de negócio, casos de uso e dependências externas, de
forma que a lógica de validação possa ser reutilizada e testada
independentemente do framework web. A API deve aceitar CPFs informados tanto com
máscara quanto sem máscara, como 123.456.789-09 ou 12345678909, e deve tratar
corretamente diferentes cenários de entrada, incluindo CPFs válidos, CPFs
inválidos por erro nos dígitos verificadores, CPFs compostos por todos os
dígitos iguais como 111.111.111-11 que são considerados inválidos por definição,
entradas contendo caracteres inesperados não numéricos, strings vazias, campos
cpf ausentes no corpo da requisição ou valores nulos. O endpoint deve retornar
respostas HTTP adequadas seguindo boas práticas de APIs REST, retornando status
code 200 quando a requisição estiver bem formada e incluindo no corpo da
resposta um JSON indicando o CPF recebido e o resultado da validação, e
retornando status code 422 quando o payload da requisição estiver malformado ou
violar as regras de validação do schema definidas com Pydantic, utilizando o
mecanismo de validação automática do FastAPI. O projeto deve incluir um arquivo
.env.example documentando todas as variáveis de ambiente utilizadas pela
aplicação, permitindo fácil configuração em diferentes ambientes. A aplicação
também deve ser totalmente containerizada, incluindo um Dockerfile otimizado
para execução da API e um arquivo docker-compose.yml que permita subir o serviço
localmente de forma simples para desenvolvimento e testes. O desenvolvimento
deve seguir a metodologia TDD, com implementação inicial de testes unitários que
cubram todos os cenários esperados de validação do CPF e validação de entrada da
API, garantindo alta cobertura de testes e evitando a implementação de testes de
integração ou testes end-to-end neste escopo inicial. Por fim, o repositório
deve incluir uma pipeline de integração contínua utilizando GitHub Actions que
execute automaticamente a instalação das dependências, rode os testes unitários,
valide o build da aplicação e garanta que o projeto permaneça estável a cada
novo commit ou pull request.
